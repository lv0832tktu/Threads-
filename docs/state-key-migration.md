# 紛失した暗号化キーの移行準備

この機能は**準備だけ**です。旧Secret、本番の暗号化ファイル、平文履歴、予約Secretsを変更しません。投稿・API取得・定期実行も行いません。新しいキーの生成や保存は自動実行しません。

## 今回追加した仕組み

- mainに `state/private-state.enc` があれば、Actionsの旧 `THREADS_STATE_KEY` で復号し、別Secretの新キーで再暗号化します。元の暗号化ファイルは別名でもコピーします。
- 暗号化ファイルがなければ、既存 `state/history.sqlite3` を読み込んで暗号化します。空の履歴を新規作成しません。
- 新しい暗号化データを復号して、全ファイルのバイト一致、SQLiteの整合性、投稿履歴の件数を検証します。公開結果不明やツリー途中の履歴も削除しません。
- 出力は `state/private-state.next.enc` と、旧暗号化ファイルがある場合のみ `state/private-state.before-migration.enc`。ログは成功・種類・件数だけです。
- ローカルの `private` フォルダがある場合は、古いmainで上書きしないよう処理を拒否します。ActionsからWindowsのデータは確認できないので、事前の手元確認が必要です。

## 承認後に行う準備手順（今は実行しない）

1. このPRを確認してmainへマージします。移行中は投稿・分析・手動競合登録など状態を書き換える操作を止めます。有効な定期ジョブがある場合も停止の承認・設定が必要です。
2. PCのThreadsフォルダ全体を、自分だけが使う場所へバックアップします。旧 `THREADS_STATE_KEY` は削除・上書きしません。
3. 新しいFernetキーを信頼できるローカルPythonで作成し、パスワード管理ソフトなどへ保管します。キー生成をCodexに依頼する場合もチャット・ログへ値を出さない方法を使ってください。キーを作り直して既存Secretへ直接上書きしないでください。
4. GitHubの Settings → Secrets and variables → Actions → New repository secret で、**`THREADS_STATE_KEY_NEXT`** を追加します。保存してから値を読み戻せないので、手元にも確実に保管します。
5. Actions → **Prepare state key migration (no activation)** → Run workflow。mainを選び、`confirm_prepare` をチェックして実行します。これは将来の明示承認後に行います。
6. 成功ログの `verified: true` と履歴件数を確認します。失敗したらキーやファイルを削除せず停止してください。旧キーが暗号化データと合わなければ移行できません。
7. 実行結果のArtifactsから `encrypted-state-migration-…` をダウンロードし、解凍して秘密のバックアップ先へ保存します。中身は暗号化ファイルだけです。Artifactは7日後に期限切れになるので、その前に保存してください。

## ここで止めて確認する

候補ファイルを作っただけでは管理画面のキーは切り替わりません。**本番ファイルとSecretを切り替える処理は、この機能にはありません。** 候補が最新状態と一致し、予約・公開済み・途中公開の履歴が保持されていることを確認してから、別途承認した切り替え作業を行います。GitHubの履歴とWindowsの履歴が違う場合は先に照合します。

旧暗号化ファイルのコピーだけでは、旧キーを失った後の復号はできません。旧Secretは切り替え検証完了まで残し、新キーで復号できる候補も長期保管してください。キー・平文・予約JSONはActions成果物や公開リポジトリに載せません。

`THREADS_SCHEDULE_JSON` の4つの予約Secrets、`private/posts.json` の下書き、画像はこの移行の対象外で、そのままです。古い予約の再投稿防止のため、切り替え後も自動公開を無効に保ち、履歴照合と人間の承認を済ませてから再開します。

## オフラインテスト

`python -m unittest discover -s tests -q` は一時フォルダとテスト用キーのみを使用します。本番のSecret・履歴は読み書きしません。実際の移行モジュールを手元のリポジトリで試しに実行することは避けてください。
